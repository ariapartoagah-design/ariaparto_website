# پرونده دانش و تحویل کار — Staging امن سایت آریا پرتو

**تاریخ ثبت:** 2026-11-16  
**نوع سند:** گزارش وضعیت میان‌دوره‌ای؛ نه گواهی آمادگی انتشار  
**محدوده:** فقط شاخه `staging/secure-master-review` و محیط آزمایشی مستقل Cloudflare  
**اصل حاکم:** هیچ تغییری روی Production، دامنه اصلی یا دیتابیس اصلی بدون مجوز جداگانه مجاز نیست.

## ۱. هدف و تصمیم‌های اصلی

- مرجع بررسی ظاهر سایت، فایل‌های شاخه `master` در مخزن `ariapartoagah-design/ariaparto_website` است.
- کد احراز هویت قدیمی همین شاخه امن نیست؛ **نباید آن را بدون اصلاح به Staging یا Production منتشر کرد**.
- شاخه موقت `staging/secure-master-review` از `master` ایجاد شده و برای تغییرات ایزوله Staging استفاده می‌شود؛ پس از انتقال کنترل‌شده اصلاحات، شاخه موقت قابل حذف است.
- تغییرات عمومی پس از آزمایش و بازبینی، جدا از تنظیمات اختصاصی Staging منتقل شوند؛ Merge مستقیم و کورکورانه مخزن آزمایشی با مخزن اصلی مجاز نیست.
- Cloudflare Builds برای Worker آزمایشی غیرفعال نگه داشته می‌شود. اتصال GitHub به‌خودی‌خود Deploy نیست.
- پیش از هر Deploy باید نام Worker، ID دیتابیس، فرمان Wrangler، فایل‌های عمومی و کنترل دسترسی سروری بررسی شوند.

| دامنه | `https://ariapartoagah.ir` | زیردامنه workers.dev اختصاصی Worker آزمایشی |
| دیتابیس | `ariaparto-db` | `ariaparto-master-staging-db` |
| D1 database_id | `50f936ab-901c-49c9-8ffd-bcb17daf7ef1` | `3347ed7e-91ba-42c7-a234-5b73d4292226` |
| وضعیت عملیات | بدون تغییر در این مراحل | Binding و جدول‌ها ایجاد شده‌اند |

- نسخه فعال Production در بررسی قبلی: `458ad381-21ec-4236-9ff2-49cd76c60b90` با ۱۰۰٪ ترافیک **در زمان آن بررسی**؛ برای تصمیم انتشار جدید باید دوباره صحت‌سنجی شود.
- Binding دیتابیس آزمایشی در Cloudflare با نام `DB` ثبت و در تصاویر تأیید شد. Runtime variables/secrets در تصویر مربوط به مرحله بررسی خالی بودند.
- Worker آزمایشی در زمان مشاهده ویرایشگر همچنان پاسخ `Hello World!` داشت؛ **انتشار کد سایت/احراز هویت هنوز تأیید نشده است**.
- در Cloudflare اتصال Git repository برای همین Worker به `ariapartoagah-design/ariaparto_website`، Production branch `master` ثبت شده است؛ گزینه `Disable builds` در تصویر روشن بود و Deploy Hooks وجود نداشت. انتشار دستی همچنان ممکن است، لذا غیرفعال‌بودن Build تضمین مطلق عدم Deploy نیست.
- هشدار Cloudflare درباره همگام‌سازی `wrangler.toml` با نام `ariaparto-master-staging` مشاهده شد؛ از تغییر مستقیم `wrangler.toml` شاخه اصلی خودداری شود.

## ۳. پایگاه داده Staging

طبق خروجی‌ها/تأییدهای کاربر، ۶ جدول زیر در D1 آزمایشی ایجاد شده و پرس‌وجوی فهرست جدول‌ها ۶ مورد برگردانده است:

1. `users`
2. `auth_sessions` — نگهداری `token_hash`، زمان انقضا و ارجاع به کاربر
3. `auth_otp_challenges` — ۱۲ ستون با بررسی `PRAGMA table_info` در تصویر تأیید شده‌اند: `phone`, `purpose`, `code_hash`, `expires_at`, `attempts`, `verified_at`, `created_at`, `verified_expires_at`, `flow_hash`, `proof_hash`, `consumed_at`, `delivery_state`
4. `auth_rate_limits` — جدول شمارش و زمان بازنشانی محدودیت
5. `user_upgrade_requests`
6. `user_history`

- ستون `delivery_state` پیش‌فرض `failed` دارد.
- ایجاد جدول‌ها به‌تنهایی به معنی اجرای صحیح OTP یا فعال‌شدن Rate Limit نیست.
- ساختار مبتنی بر Migrationهای مخزن `ariapartoagah-design/ariaparto-auth-test` بررسی شد؛ پیش از آزمون یکپارچه، همخوانی تمام ایندکس‌ها، قرارداد SQL و مسیرهای Worker با اسکیمای فعلی باید راستی‌آزمایی شود.
- هیچ داده کاربران Production نباید به Staging کپی شود.

## ۴. سیاست مصوب OTP و کاوه‌نگار برای Staging

این مقادیر **مصوب ولی هنوز پیاده‌سازی/راستی‌آزمایی عملی نشده‌اند**:

| کنترل | مقدار |
|---|---|
| سقف هر موبایل | ۳ درخواست در ساعت |
| سقف هر IP | ۵ درخواست در ساعت |
| سقف کل Staging | ۱۰ پیامک در روز |
| حداقل فاصله درخواست مجدد | ۶۰ ثانیه |
| اعتبار OTP | ۱۲۰ ثانیه |
| تعداد تلاش تأیید | حداکثر ۵ بار |
| شماره‌های مجاز | فقط شماره‌های آزمایشی صریحاً تأییدشده |

- کاربر خواسته آزمون نهایی با کاوه‌نگار واقعی انجام شود، نه Mock؛ با این حال **هیچ پیامک واقعی در این مرحله ارسال نشده است**.
- قبل از ارسال واقعی، باید Allowlist شماره، قفل یک‌بارمصرف، کنترل هزینه/سقف، ثبت رویداد بدون اطلاعات حساس و تأیید جداگانه برای آزمون محدود وجود داشته باشد.
- کلیدهای محرمانه نباید در GitHub یا متن گفتگو منتشر شوند؛ فقط Secret اختصاصی Worker آزمایشی.

## ۵. وضعیت GitHub و فایل‌ها

- مخزن اصلی: `ariapartoagah-design/ariaparto_website`
- شاخه‌های موجود در آغاز کار: `main` (default) و `master` (دارای اختلاف تاریخچه/محتوا).
- شاخه جدید: `staging/secure-master-review`، منشأ `master`، از طریق GitHub UI ساخته شده است.
- Commit `33f2206` با پیام `chore: add isolated staging configuration`: فایل `wrangler.staging.toml` ثبت شده.
- Commit `01f7331` با پیام `chore: initialize staging public directory`: فایل `public/health.txt` ثبت شده.
- در زمان ثبت سند، فایل `wrangler.staging.toml` شامل موارد زیر است:
  - `name = "ariaparto-master-staging"`
  - `main = "src/index.js"`
  - `workers_dev = true`
  - Binding `DB` به `ariaparto-master-staging-db` با ID آزمایشی بالا
  - `[assets]` با `directory = "./public"` و `binding = "ASSETS"`
- فایل `wrangler.toml` قدیمی شاخه `master` به `name = "ariaparto-website"` و ID دیتابیس اصلی اشاره می‌کند. **اجرای بی‌قید `npx wrangler deploy` از آن خطر انتشار اشتباه دارد.**
- پوشه `public` فعلاً فقط فایل آزمایشی `health.txt` را دارد؛ مسیرهای واقعی HTML/JS هنوز منتقل نشده‌اند.
- فایل‌های ظاهری سایت در ریشه مخزن هستند؛ پوشه `.wrangler/state` و فایل‌های محلی/غیرعمومی نیز در تاریخچه شاخه دیده شدند؛ نباید کل ریشه به عنوان دارایی عمومی منتشر شود.
- ساخت `public` با حداقل فایل‌های مجاز و محافظت سمت سرور برای صفحات حساس ضروری است. صرف وجود `public` یا فایل `.assetsignore`، حفاظت مسیرهای حساس را اثبات نمی‌کند.
- چون کانفیگ اصلی و Staging جدا هستند، فرمان انتشار آینده باید **صریحاً** کانفیگ Staging را انتخاب کند؛ هیچ فرمان Deploy قبل از بازبینی و مجوز مجزا اجرا نشود.

## ۶. بررسی فقط‌خواندنی صفحه اصلی `index.html`

فایل HTML ارائه‌شده از سوی کاربر بررسی شد:
- CSS عمدتاً داخل همان HTML است؛ حالت روشن/تاریک در اسکریپت داخلی مدیریت می‌شود.
- لینک‌های نسبی به `about.html`, `contact.html`, `login.html` و `services.html` نیاز دارند که مسیرهای مقصد همراه فایل‌های عمومی/امن هماهنگ شوند.
- وضعیت ورود صرفاً از `localStorage.user_logged_in` خوانده می‌شود و خروج فقط اطلاعات localStorage را پاک می‌کند؛ برای Staging امن باید وضعیت نشست از API معتبر سرور خوانده شود و خروج نشست را در D1 باطل کند.
- ثبت درخواست به Google Apps Script با `fetch(..., {mode:'no-cors'})` انجام می‌شود؛ نمایش موفقیت بعد از Promise پاسخ، موفقیت واقعی ثبت را اثبات نمی‌کند.
- آمار ۱۲ پروژه، ۳۴ تأمین‌کننده و ۵ معامله این هفته مقادیر ثابت داخل HTML هستند و پیش از انتشار باید صحت/نمایشی‌بودن آنها تعیین شود.
- ظاهر صفحه قرار است تا حد امکان ثابت بماند؛ منطق ورود/خروج/فرم باید جداگانه و با تست اصلاح شود.

## ۷. خطرهای شناخته‌شده در شاخه `master`

در بررسی قبلی:
- `src/index.js` کد OTP با `Math.random` و ثبت/لاگ کد خام دارد، جدول قدیمی `otps` را می‌خواند و Session را به شکل Base64 بدون امضای معتبر می‌سازد؛ کوکی Secure مناسب ندارد. **این کد نباید Deploy شود.**
- `src/index.js` همچنین برای فایل‌های سایت `env.ASSETS.fetch(request)` را فراخوانی می‌کند.
- `js/auth.js` و برخی صفحات به localStorage متکی‌اند، و کنترل کاتالوگ‌ها صرفاً سمت مرورگر است.
- قراردادهای Login/Register/Logout و `/api/auth/me` باید با Worker امن مبتنی بر D1 تطبیق یابند.
- صفحات کاتالوگ محافظت‌شده نباید از طریق درخواست مستقیم URL قابل دریافت باشند؛ کنترل سمت Worker و بررسی اولویت سرو Static Assets لازم است.
- تغییرات آزمایشی قبلی در مخزن `ariaparto-auth-test`، پیش‌نویس PR #7 با اصلاحات امنیتی/صفحات، وجود دارد؛ **نه Merge شده و نه مستقر شده**. برای استفاده، diff و تست‌های آن دوباره با کد این مخزن تطبیق داده شوند؛ ادعای آماده‌بودن Production از موفقیت تست‌های Mock استنباط نشود.

## ۸. وضعیت واقعی، کارهای باز و نقطه ازسرگیری

**انجام‌شده و شواهد آن:** ایجاد Staging Worker، D1 مجزا و Binding؛ ایجاد جداول و تأیید ۱۲ ستون OTP؛ اتصال GitHub با Disable builds روشن؛ ایجاد شاخه موقت؛ ثبت فایل کانفیگ آزمایشی؛ ایجاد `public/health.txt`؛ بررسی محتوای صفحه اصلی.

**انجام‌نشده/نیازمند تأیید:** راه‌اندازی امن Worker جدید؛ انتقال/بازسازی دارایی‌های عمومی؛ رفع تمام وابستگی‌های HTML؛ اجرای کنترل دسترسی سمت Worker؛ فعال‌سازی Rate Limit و Allowlist؛ اتصال Secret کاوه‌نگار؛ اجرای آزمون واقعی OTP؛ آزمون یکپارچه UI/API؛ هرگونه Deploy نهایی، Merge یا تغییر Production.

**گام بعدی پیشنهادی:** از کدهای `master` و `ariaparto-auth-test`، نقشه فایل‌های عمومی و مسیرهای محافظت‌شده را استخراج کنید؛ سپس طرح امن ورود/خروج/OTP و نسخه Staging فایل‌های عمومی را در شاخه موقت آماده کرده و پیش از Deploy با تست‌های مشخص بررسی کنید. از انتشار مستقیم `src/index.js` قدیمی خودداری کنید.

## ۹. قواعد ایمنی ادامه کار

1. ابتدا هر دستور Deploy را با بررسی نام Worker، فایل `--config`، D1 ID، مجوز، Build و Asset Directory کنترل کنید.
2. مخزن/شاخه `main` و `master` بدون مجوز جداگانه تغییر نکنند.
3. هیچ اطلاعات خصوصی کاربران و کلید API در Git ثبت نشود.
4. آزمون پیامک واقعی فقط پس از فعال‌سازی گیت امنیتی و تأیید محدوده ارسال.
5. «پیکربندی ثبت شد»، «Build پاس شد»، «Deploy شد» و «آزمون واقعی موفق شد» چهار وضعیت مستقل‌اند؛ هیچ‌کدام به‌جای دیگری گزارش نشود.
